# CCC Planner

Сервис планирования спринтов поверх Jira: тянет задачи по кнопке, считает приоритет (WSJF), часы и **нагрузку каждого человека за спринт**, не даёт молча перегрузить команду и показывает, что можно взять в работу, а что ещё не готово (Definition of Ready).

C# / .NET 8, Blazor Server, PostgreSQL, всё запускается одной командой в Docker. Работает локально, Jira только читает.

## Быстрый старт

```bash
git clone <этот репозиторий>
cd ccc-planner
cp .env.example .env      # впишите JIRA_BASE_URL, JIRA_EMAIL, JIRA_API_TOKEN, JIRA_PROJECT_KEY
docker compose up -d --build
```

Откройте http://localhost:8085. Без токена сервис стартует на демонстрационных данных (12 вымышленных задач): можно сразу посмотреть интерфейс. Другой порт: `PLANNER_PORT=8090 docker compose up -d`.

Токен Jira Cloud: https://id.atlassian.com/manage-profile/security/api-tokens (достаточно прав на чтение). Токен лежит только в `.env`, в интерфейс и образ не попадает, файл в `.gitignore` и `.dockerignore`.

## Возможности

| Раздел | Что делает |
|---|---|
| **Планирование** | Три блока как в беклоге Jira: текущий спринт, следующий спринт (пред-спринт) и беклог по WSJF. Нагрузка людей справа. Задачи можно перетаскивать мышью между блоками, выделять галочками и двигать группой. «Перевести готовые в текущий» проверяет DoR и ёмкость |
| **Доска** | Текущий спринт по колонкам статусов и нагрузка по исполнителям. Задача пропала из Jira, значит закрыта, но в сервисе остаётся |
| **Приоритеты бизнеса** | Файл заказчика (Excel/CSV) кладётся в папку `inbox`, сервис сам подбирает похожие задачи беклога и добавляет баллы к Business Value |
| **Команда** | Ёмкость каждого в часах на спринт и часы на встречи и инциденты |
| **⬇ Excel** | Кнопка в верхней панели (или `/export/xlsx`): все задачи по блокам, нагрузка людей, команда и приоритеты бизнеса одним файлом |

Синхронизация идёт только по кнопке «Синхронизировать». Данные между нажатиями хранятся в PostgreSQL.

## Как считается

**Исполнитель в Jira** по умолчанию разработчик. Если исполнитель аналитик и анализа ещё нет, задача аналитическая (часы у аналитика). Если анализ готов, у задачи метка «нужен разработчик». Задачи без исполнителя или у людей не из списка команды попадают в блок «Работа вне команды».

**Готовность к спринту (DoR).** В следующий спринт можно положить что угодно. Чтобы перевести в текущий, нужны: описание или вложение, разработчик, аналитик (если анализ нужен), оценка в часах и свободная ёмкость у обоих. Критерии приёмки не обязательны, но без них анализ не считается сделанным, и аналитик получает часы на анализ.

**Нагрузка за спринт** (закрытые задачи остаются в ней):
- разработчик: часы его задач (включая закрытые и в Backlog) плюс встречи и инциденты;
- аналитик: свои аналитические задачи, анализ пред-спринта, анализ вне спринта, сопровождение (15% от часов разработки, 25% у интеграций, с момента, когда разработчик взял задачу) и встречи.

**Часы анализа** считаются по содержанию задачи: база 6 или 10 ч, плюс интеграция +8 ч, маппинг данных и примеры запросов +8 ч, уточнения +4 ч, документация +4 ч, интеграторы +12 ч, нет критериев +4 ч. Поле «Ждём ответа от» часы не снижает, а резервирует. Введённые вручную часы всегда главнее.

**WSJF** = (Business Value + Time Criticality + Risk Reduction + бонус бизнеса) / Job Size. Job Size из часов: до 4 ч это 1, до 8 это 2, до 16 это 3, до 40 это 5, до 80 это 8, больше это 13. Бонус бизнеса: приоритет 1 даёт +13, 2 +8, 3 +5, 4 +3, 5 +1.

## Настройка

| Переменная `.env` | Значение |
|---|---|
| `JIRA_BASE_URL`, `JIRA_EMAIL`, `JIRA_API_TOKEN` | доступ к Jira Cloud |
| `JIRA_PROJECT_KEY` | ключ проекта; из него строятся запросы по умолчанию |
| `JIRA_JQL`, `JIRA_SPRINT_JQL` | свои запросы вместо запросов по умолчанию (например, под фильтр вашей доски) |
| `DEFAULT_CAPACITY_HOURS` | ёмкость по умолчанию, часов на человека за спринт (50) |
| `SUPPORT_PERCENT` | сопровождение аналитика, % от часов разработки (15) |
| `PLANNER_PORT` | порт на хосте (8085) |

Люди, роли и их ёмкость задаются на вкладке «Команда». Имена должны совпадать с displayName в Jira. Ключевые слова интеграций для оценки анализа лежат в `src/Planner/Services/Rules.cs` (список `Systems`), подберите их под свой домен.

## Файл бизнес-заказчика

Положите xlsx или csv в папку `inbox`. Через ~10 секунд сервис разберёт строки («N приоритет», «приоритет N», число 1 до 9 в ячейке, high/medium/low), подберёт задачи по словам темы и переложит файл в `inbox/processed` (или в `inbox/failed` с причиной). Новая версия файла с тем же именем заменяет прежнюю, а ваши галочки у совпадений сохраняются.

## Ограничения

- Схема БД создаётся через `EnsureCreated` и небольшие `ALTER TABLE`; при больших изменениях модели проще пересоздать базу (`docker compose down -v`).
- Авторизации нет: сервис рассчитан на закрытую сеть или локальный запуск.
- Оценки часов предварительные: их подтверждает команда.
- Состав спринта в Jira сервис не меняет. Переведённые в сервисе задачи помечаются «переведена здесь», пока Jira не добавит их в спринт.
- Docker и .NET SDK: локально нужен только Docker, сборка идёт в контейнере.
